# UI 状态与控件分离

**小界面硬编码没问题，界面一长大就失控。解法：把数据（状态）和可见控件分开，两者只通过信号通信。**

## 硬编码反模式

最直接的写法是把所有交互塞进一个脚本：选英雄时手动给每个 Label 赋值，改名时手动回写列表项，雇佣时手动改两个列表。

```gdscript
# 反模式：一个脚本同时管数据和所有控件
func _on_hero_selected(idx: int):
    var h := heroes[idx]
    $Center/Name.text = h.name
    $Center/Strength.text = str(h.strength)
    $Center/Wisdom.text = str(h.wisdom)
    $LeftList.select(idx)

func _on_name_changed(new_text: String):
    selected_hero.name = new_text
    $LeftList.item_text = new_text  # 手动同步每一处显示
```

界面简单时能跑。问题随规模放大：

| 症状 | 原因 |
|---|---|
| 改一个字段要翻多处赋值 | 数据散落在控件逻辑里 |
| 新增一个显示位置要改原函数 | 显示和数据绑死 |
| 控件之间互相引用 | 移除一个按钮牵连一片 |
| 逻辑无法独立测试 | 离开场景树就跑不动 |

## 两个概念

| 概念 | 是什么 | 例子 |
|---|---|---|
| **状态 State** | UI 要影响的全部数据 | 两个英雄数组、当前选中项、每个英雄的名字/力量/智慧 |
| **控件 Control** | 玩家可见、可交互的节点 | Button、Label、LineEdit、列表、复选框 |

目标：状态变化就更新控件，控件变化就更新状态。控件之间互不知道对方存在，只和状态说话。

## 信号驱动的双向流

```
控件输入 ──(控件自身信号)──▶ 更新状态
                              │
状态变化 ──(状态自定义信号)──▶ 更新控件
```

- 玩家在 LineEdit 打字 → 控件发 `text_changed` → 回调改状态
- 状态里的名字变了 → 状态发 changed 信号 → 回调把新值写进所有显示它的控件

控件不直接调另一个控件，也不直接读另一个控件。这条规则是可维护性的核心。

## 为什么用信号而不是直接调用

> 值得注意的是：这是观察者模式在 Godot 的落地。发送方（控件或状态）不知道谁在监听，接收方也不需要持有发送方引用。删掉任意一个控件，其余部分照常工作，因为它们只依赖状态。

| 直接调用 | 信号通信 |
|---|---|
| A 持有 B 的引用 | A 只发信号，不认识 B |
| 删 B 要改 A | 删 B 不影响 A |
| 多个监听者要 A 逐个调 | A 发一次，所有监听者各自响应 |

## 三层划分（官方社区共识）

成熟做法把 UI 拆成三层，和 MVC/MVVM 同源：

| 层 | 职责 | 载体 |
|---|---|---|
| 数据层 | 纯数据，不含显示逻辑 | Resource / 普通对象 |
| 逻辑层 | 持有唯一数据副本，提供操作 | autoload 单例或状态节点 |
| 视图层 | 只负责显示和转发输入 | Control 子树 |

视图层不存业务数据，只从状态读、向状态写。这样换一套 UI 皮肤，数据层一行不改。

## 这套属于哪个模式

严格说它缺一个独立中介（Controller/Presenter），View 的信号回调直接改状态，归为**被动模型 + 观察者**，近似 MVVM-lite，社区口语常笼统叫 MVC。三种经典模式的完整对比见[UI 范式全景](00-paradigm-survey.md)。

## 什么时候不需要这套

> 值得注意的是：**单屏菜单、HUD 血条这种一两个控件的界面，直接在脚本里赋值更快**。状态分离的成本是一层封装，收益在界面有多个互相联动的显示位置（列表 + 详情 + 可编辑字段）时才兑现。不要为一个按钮上这套。
